Generated FROM the manifest by `helix_code/scripts/extensions_catalog/generate_catalog.py` — **never hand-transcribed** — with a real, live filesystem probe per skill × platform cell, never a blank cell (§11.4.201(6)).

**Closed status vocabulary** (§11.4.228(A)(1)): `SUPPORTED` (verified working, real per-platform liveness probe this run) / `CONFIG-ONLY` (declared — this platform HAS a registrar targeting it — but not currently wired) / `UNTESTED` (this platform has NO registrar/wiring mechanism reaching this skill at all — an honest §11.4.197-tracked gap) / `UNSUPPORTED` (proven structurally impossible per §11.4.112 — unused by this generator; no platform here has been proven incapable of loading a Markdown-frontmatter skill).

**HelixCode column — three distinct facts, not one (HXC-159 T-P9.01 round-4 F-22(b) correction).** The HelixCode cell's `SUPPORTED` / `CONFIG-ONLY` status still reports the SAME thing it always has — whether the skill is *reachable via `.claude/skills/` by some tier* (a directory-presence probe). That status alone does NOT establish either of two further, independently live-probed facts, each also-true and each distinct: (1) whether the skill is specifically *ADMITTED by the external tier's own similarity-conflict policy gate* (live-probed via `submodules/helix_agent/cmd/similarity-probe`, the SAME code path `Load()` uses); and (2) — for a skill the gate DOES admit — whether the FINAL registry a user actually gets skills from serves it FROM the external tier or from a same-named, independently-loaded `builtin` copy that overrides it (live-probed via a real `helixcode skills list`, HXC-159 F-22(a)'s root cause: `loadBuiltinSkills` runs on every load, last). Every Per-skill-detail note below states ALL applicable facts explicitly and honestly — never hand-transcribed, §11.4.6 — including when either probe itself could not run this run, in which case the note says so rather than silently reusing a stale or assumed verdict.
